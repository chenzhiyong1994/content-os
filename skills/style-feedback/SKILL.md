# 内容反馈闭环

## 先读

- `docs/operations/feedback-loop.md`
- `docs/references/style-profile.md`
- `docs/references/content-feedback-library.md`

## 核心职责

每次用户对稿子做出修改、审核意见或发布前校准时，先修当前产物，再把可复用的判断沉淀到合适位置。

本 skill 不只处理“是否贴合作者声音”。它处理人的审核反馈闭环：

```text
用户反馈 / 手动修改
-> 识别修改意图
-> 修当前稿
-> 分类反馈
-> 更新风格画像、案例库或流程技能
```

核心不是记录原话，而是**归纳**：从具体修改里找出下次可复用的写作、平台或工作流判断。

---

## 触发时机

- 用户手动改了某段内容，并说明为什么改
- 用户说"不像我""不是我风格""这句不对"
- 用户说"标题不行""开头太慢""这段没必要""这个适合小红书/不适合公众号"
- 用户在修改过程中透露了风格偏好
- 用户对比两个版本，指出差异
- 用户在微信公众号草稿箱中手动校准后，待发布源稿回读得到与上传前终稿不同的正文
- 同一类问题在多次内容流程中反复出现

---

## 反馈类型

### 直接反馈
- 用户明确说"改成XXX"
- 用户说"这里不对，原因是YYY"

### 间接反馈
- 用户修改了某段，但没说原因 → 需要我反向推断
- 用户在两个方案中选了A没有选B → 需要我理解为什么
- 用户说"这句读起来OK，但下一句突然变了" → 暴露了节奏偏好

### 草稿箱回读反馈
- `reviewed-source.md` 与上传前 `05_最终稿` 的标题、正文、结构、语气、删减或强调发生实质差异
- 需要忽略 HTML 样式、固定尾注、公众号分割线、图片位置、上传排版自动加入的小标题和其他自动排版噪音
- 用户手动改写的草稿箱小标题只归类为 `platform-fit`，不更新正文创作规则

---

## 分类路由

先按 `docs/operations/feedback-loop.md` 分类，再决定沉淀位置。

| 反馈类型 | 典型内容 | 处理方式 |
| --- | --- | --- |
| `style` | 作者声音、标题气口、开头/结尾、节奏、措辞 | 更新 `docs/references/style-profile.md` |
| `content-logic` | 判断缺少材料支撑、证据不足、解释链过长、结构顺序不对 | 优先更新当前稿；必要时写入 `docs/references/content-feedback-library.md` |
| `platform-fit` | 微信手机端阅读、小红书适配、标题传播、配图包装 | 写入案例库；重复出现时更新相关 skill |
| `workflow` | 阶段顺序、gate、回读、交接、验证机制问题 | 修改 `docs/operations/workflow-rules.md` 或相关 skill |
| `anti-pattern` | AI 腔、伪具体、顺滑空话、模板标题 | 更新风格画像、审稿 skill 或案例库 |
| `one-off` | 只对当前文章成立 | 只改当前稿，不更新长期规则 |

---

## 执行流程

1. **读取反馈上下文**：确认当前文章、阶段、内容类型和用户修改来源。
2. **修当前产物**：如果用户要求修改当前稿，先完成本次修改。
3. **识别反馈**：从用户话语、手动修改或 reviewed-source diff 中识别真实意图。
4. **分类路由**：按反馈类型判断应该更新画像、案例库、skill，还是只记在当前稿。
5. **归纳规则或案例**：把具体修改翻译成可复用的规则、案例或反模式。
6. **更新目标文件**：只更新必要文件，避免重复沉淀。
7. **确认学习结果**：告诉用户这次沉淀到了哪里，以及哪些内容没有持久化。

当反馈来自待发布源稿回读时，先对比上传前 `05_最终稿` 与回读后的 `reviewed-source.md`，再归纳规则或案例。对比时只沉淀用户主动修改出的标题、正文、结构、节奏、语气或平台适配差异，不把公众号 HTML 样式、固定尾注、上传排版自动小标题或其他自动排版噪音当成偏好。用户手动改写的小标题只服务公众号平台适配，不反向改变正文创作结构。

---

## 规则沉淀标准

不是记录"这句话怎么改"，而是记录"这类情况怎么处理"。

| 用户说 | 应该沉淀为 |
|--------|-----------|
| "这句太像一个编辑在总结了，不像我" | 不要用总结式句子结尾，避免把判断提前 |
| "收尾收得太满了，不要给结论" | 收尾留开放感，不要给解决方案或总结句 |
| "这个词太书面了" | 优先用口语化词汇，不要用"因此""然而"等书面连接词 |
| "这段逻辑跳了" | 每个判断必须经过场景铺垫，不能直接跳到结论 |

## 画像更新格式

当反馈属于 `style` 或强相关 `anti-pattern` 时，按以下格式追加到 `docs/references/style-profile.md`：

```markdown
## 迭代记录 YYYY-MM-DD

### 反馈来源
[用户的原话或修改描述]

### 归纳规则
[从具体修改中归纳出的可复用规则]

### 适用场景
[这个规则在什么情况下适用]
```

---

## 案例库更新格式

当反馈更适合用前后对照保存，或还不足以成为全局规则时，写入 `docs/references/content-feedback-library.md` 的对应区块：

```markdown
### YYYY-MM-DD - [短案例名]

- Content type:
- Stage:
- Source:
- User feedback:
- Before:
- After:
- Learned pattern:
- Applies when:
- Do not apply when:
- Confidence:
- Follow-up:
```

案例库可以收低置信度观察；风格画像不收低置信度观察。

## Skill 更新条件

只有满足以下任一条件，才修改项目 skill 或流程规则：

- 同类问题至少在两次独立内容流程中出现
- 问题严重到后续流程应该主动拦截
- 当前 skill 的提示方式直接导致了问题
- 用户明确要求把反馈变成流程规则

修改 skill 时要保持窄范围，并在最终回复列出具体改动。

---

## 注意事项

- 只沉淀用户主动给出的反馈，不主动猜测
- 规则要具体到可执行，不要写成"更像人话"这种空话
- 不要把一次文章里的战术取舍升级成全局规则
- 不要把同一条学习同时写入多个长期文件，除非它在不同文件里承担不同作用
- 每次沉淀后告诉用户，让用户知道系统学到了什么

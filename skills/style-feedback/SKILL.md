# 内容反馈闭环

## 先读

- `docs/operations/feedback-loop.md`
- `docs/references/style-profile.md`
- `docs/references/content-feedback-library.md`

## 核心职责

用户要求修改当前稿时，先修当前产物，再把可复用的判断沉淀到合适位置。草稿箱回读只服务风格画像，直接按下方“草稿箱回读反馈”执行，不进入通用修稿或技能迭代流程。

本 skill 不只处理“像不像作者”。它处理人的审核反馈闭环：

```text
用户反馈 / 手动修改
-> 识别修改意图
-> 修当前稿
-> 分类反馈
-> 更新风格画像、案例库或流程技能
```

核心不是记录原话，而是**归纳**：从具体修改里找出下次可复用的写作、平台或工作流判断。

---

## 触发时机

- 用户手动改了某段内容，并说明为什么改
- 用户说"不像我""不是我风格""这句不对"
- 用户说"标题不行""开头太慢""这段没必要""这段不适合公众号"
- 用户在修改过程中透露了风格偏好
- 用户对比两个版本，指出差异
- 用户在微信公众号草稿箱中手动校准后，风格回读得到与上传基线不同的表述或断句
- 同一类问题在多次内容流程中反复出现

---

## 反馈类型

### 直接反馈
- 用户明确说"改成XXX"
- 用户说"这里不对，原因是YYY"

### 间接反馈
- 用户修改了某段，但没说原因 → 需要我反向推断
- 用户在两个方案中选了A没有选B → 需要我理解为什么
- 用户说"这句读起来OK，但下一句突然变了" → 暴露了节奏偏好

### 草稿箱回读反馈

直接执行 `docs/operations/feedback-loop.md` 的“草稿箱回读：仅用于风格画像”。使用脚本返回的上传文本基线与修改后样本，观察措辞、标点、断句、分段和语气，不看格式细节。

本分支只更新有证据的风格画像及必要的对照案例；不改当前草稿，不触发下方平台、流程或 skill 更新路由。基线缺失或不属于同一草稿时，不猜测人工修改。

---

## 分类路由

先按 `docs/operations/feedback-loop.md` 分类，再决定沉淀位置。

| 反馈类型 | 典型内容 | 处理方式 |
| --- | --- | --- |
| `style` | 作者声音、标题气口、开头/结尾、节奏、措辞 | 更新 `docs/references/style-profile.md` |
| `content-logic` | 判断缺少材料支撑、证据不足、解释链过长、结构顺序不对 | 优先更新当前稿；必要时写入 `docs/references/content-feedback-library.md` |
| `platform-fit` | 微信手机端阅读、标题传播、配图包装 | 写入案例库；重复出现时更新相关 skill |
| `workflow` | 阶段顺序、gate、回读、交接、验证机制问题 | 修改 `docs/operations/workflow-rules.md` 或相关 skill |
| `anti-pattern` | AI 腔、伪具体、顺滑空话、模板标题 | 更新风格画像、审稿 skill 或案例库 |
| `one-off` | 只对当前文章成立 | 只改当前稿，不更新长期规则 |

## 通用反馈执行流程（不适用于仅回读学习）

1. **读取反馈上下文**：确认当前文章、阶段、内容类型和用户修改来源。
2. **修当前产物**：如果用户要求修改当前稿，先完成本次修改。
3. **识别反馈**：从用户话语或明确要求分析的手动修改中识别真实意图。
4. **分类路由**：按反馈类型判断应该更新画像、案例库、skill，还是只记在当前稿。
5. **归纳规则或案例**：把具体修改翻译成可复用的规则、案例或反模式。
6. **更新目标文件**：只更新必要文件，避免重复沉淀。
7. **确认学习结果**：告诉用户这次沉淀到了哪里，以及哪些内容没有持久化。

## 规则沉淀标准

先记录具体差异与适用场景，再判断它是否能改变长期规则。下面只是分类方向，不是从一句反馈直接推广出的通用禁令。

| 用户说 | 应该沉淀为 |
|--------|-----------|
| "这句太像一个编辑在总结了，不像我" | 检查当前结尾是否重复总结，保留已成立的作者判断 |
| "收尾收得太满了，不要给结论" | 当前稿尝试提前结束；是否形成长期偏好须看题材与重复证据 |
| "这个词太书面了" | 改当前不贴合语境的措辞，不据此禁止所有书面连接词 |
| "这段逻辑跳了" | 补齐缺少的证据或推理，不强行增加场景 |

## 画像更新格式

当反馈属于有充分证据的 `style` 或强相关 `anti-pattern` 时，改写 `docs/references/style-profile.md` 中最近的现役条款，并标明适用边界。删除被新规则替代的旧说法，不追加日期日志。

原话、前后对照、来源、适用范围和置信度按下方案例格式记录；已有案例时更新同一条。历史案例只用于追溯，不能覆盖现役画像。

---

## 案例库更新格式

当反馈更适合用前后对照保存，或还不足以成为全局规则时，写入 `docs/references/content-feedback-library.md` 的对应区块：

```markdown
### YYYY-MM-DD - [短案例名]

- Content type:
- Stage:
- Source:
- User feedback:
- Before:
- After:
- Learned pattern:
- Applies when:
- Do not apply when:
- Confidence:
- Follow-up:
```

案例库可以收低置信度观察；风格画像不收低置信度观察。

---

## Skill 更新条件

只有满足以下任一条件，才修改项目 skill 或流程规则：

- 同类问题至少在两次独立内容流程中出现
- 问题严重到后续流程应该主动拦截
- 当前 skill 的提示方式直接导致了问题
- 用户明确要求把反馈变成流程规则

修改 skill 时要保持窄范围，并在最终回复列出具体改动。

---

## 注意事项

- 以用户反馈或真实手动差异为证据；用户没有说明原因时可以记录推断，但需标明置信度，不把推断当成明确授权的长期偏好
- 规则要具体到可执行，不要写成"更像人话"这种空话
- 不要把一次文章里的战术取舍升级成全局规则
- 不要把同一条学习同时写入多个长期文件，除非它在不同文件里承担不同作用
- 每次沉淀后告诉用户，让用户知道系统学到了什么
